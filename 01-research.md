# Задание 1. Исследование моделей и инфраструктуры

## Контекст

QuantumForge Software — финско-эстонская компания (ЕС, GDPR), у неё ~21 000 документов в Confluence, GitHub и PDF. Проблема: сотрудники тратят до 4 часов в неделю на поиск, документация устаревает через 2–3 месяца после релизов, а подготовка к SOC 2 audit занимает 140 часов в год. Часть документов (PDF заказных проектов) — конфиденциальна.

Заказчик решения — руководство и GRC-команда. Пользователи — разработчики, саппорт, менеджеры, новые сотрудники.

## 1. Сравнение LLM

YandexGPT исключаю из сравнения: компания финская, документация на английском, юрисдикция РФ неприемлема для EU-компании по GDPR.

| Критерий                           | Локальные (HuggingFace)                                                                                                | OpenAI                                                                                                        |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Качество ответов                   | Современные модели (Qwen 3.6, Llama 4) сопоставимы с OpenAI Mini на RAG-задачах при выборе 14B+                        | Высокое; GPT-5.4 Mini — хороший баланс цены и качества для RAG                                                |
| Скорость работы                    | Зависит от железа: на GPU быстро, на CPU медленно                                                                      | Быстро; зависит от загрузки серверов провайдера                                                               |
| Стоимость владения и использования | Высокие стартовые вложения (GPU-сервер от ~€500/мес), зато дальше фиксированная стоимость без роста с объёмом запросов | Оплата по факту: GPT-5.4 Mini ~$0.25/$2.00 за 1M токенов. Дёшево на малых объёмах, дорожает с ростом нагрузки |
| Удобство и простота развёртывания  | Сложно: нужен GPU, настройка окружения, поддержка модели своими силами                                                 | Просто: API-ключ и несколько строк кода, обновления на стороне провайдера                                     |

## 3. Сравнение векторных баз: ChromaDB и FAISS

| Критерий                                 | ChromaDB                                                                                                     | FAISS                                                                 |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| Скорость поиска и индексации             | Немного медленнее FAISS, но разница незаметна на базах до 1M документов                                      | Один из самых быстрых, заточен именно под поиск по векторам           |
| Сложность внедрения и поддержки          | Чуть сложнее на старте (нужен отдельный сервис), но потом проще: добавление и удаление документов из коробки | Простой старт; добавление новых документов требует пересборки индекса |
| Удобство в работе                        | Есть фильтрация по метаданным (источник, дата), встроенное хранение на диске                                 | Только поиск по вектору; всё остальное — вручную                      |
| Стоимость владения (учёт инфраструктуры) | Бесплатно; нужен небольшой контейнер и место на диске                                                        | Бесплатно; работает в памяти, дополнительной инфраструктуры не нужно  |

## 4. Конфигурация сервера и итоговые рекомендации

### Варианты архитектуры

| Вариант              | Стек                                                                                                | Сервер                            | Стоимость/мес | Сложность     |
| -------------------- | --------------------------------------------------------------------------------------------------- | --------------------------------- | ------------- | ------------- |
| A. Полное облако     | OpenAI LLM + OpenAI Embeddings + FAISS                                                              | 2 vCPU, 4–8 GB RAM, без GPU       | ~$80–120      | Низкая        |
| B. Облако + ChromaDB | OpenAI LLM + OpenAI Embeddings + ChromaDB                                                           | 2–4 vCPU, 8–16 GB RAM, без GPU    | ~$100–150     | Средняя       |
| C. Гибрид            | OpenAI (общие документы) + локальный Qwen 14B (конфиденциальные) + Sentence-Transformers + ChromaDB | 16 vCPU, 64 GB RAM, 1× GPU        | ~€800–1200    | Высокая       |
| D. Полная локальная  | Qwen 3.6 27B + Sentence-Transformers + ChromaDB                                                     | 32 vCPU, 128 GB RAM, 1× A100 80GB | ~€2000–3000   | Очень высокая |

### Рекомендация: Вариант A

Для текущей задачи выбираю **Вариант A — полное облако с FAISS**.

Вариант B отличается от A только заменой FAISS на ChromaDB, что усложняет развёртывание, но не даёт видимого преимущества на этапе MVP: база документов QuantumForge невелика (~400k чанков), и скорость поиска FAISS для неё более чем достаточна. ChromaDB имеет смысл при переходе в продакшн, когда документы начнут регулярно обновляться.

Вариант C решает реальную проблему конфиденциальности, но требует GPU-сервера и DevOps-экспертизы. Это следующий шаг, а не стартовая точка.

Вариант D избыточен: 200 сотрудников не создают нагрузку, которая требует локального 70B-класса. Затраты не оправданы.

Вариант A позволяет запустить бота быстро, проверить гипотезу в реальном использовании и уже на основе данных решить — стоит ли переходить на более сложный стек. Сервер без GPU дёшев, OpenAI берёт на себя инфраструктуру и обновления моделей.

### Итоговый стек

- **LLM:** OpenAI GPT-5.4 Mini
- **Эмбеддинги:** OpenAI text-embedding-3-small
- **Векторная база:** FAISS
- **Сервер:** 2 vCPU, 4–8 GB RAM, без GPU (AWS t3.medium или аналог)
